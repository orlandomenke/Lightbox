# Bugs

What is wrong, and what would prove it is not.

**The checkboxes are derived, not typed.** Every entry names the regression
test that must exist for the bug to be closed, and
`python3 scripts/bugs.py sync` resolves that against
`.claude/codemap/map.json` and rewrites the mark.

| | meaning |
| --- | --- |
| `[ ]` | open — the test does not exist, or does not resolve |
| `[x]` | fixed — every named test resolves |

Deleting the test reopens the bug on the next run. That is the property worth
having: a bug marked fixed with nothing guarding it is worse than an open bug,
because it stops anyone looking.

**Placement is derived too.** Open entries live under `## Open`, fixed ones
below the rule under `## Fixed`, and `sync` moves them — so the top of the file
is always what is still wrong, however long the file gets. That was written down
as already true for a while before it was: `## Fixed` carried the sentence
"entries move here when sync closes them" while sync only ever rewrote a
checkbox in place, so closed bugs piled up at the top and the section meant to
hold them stayed empty. Both sections are sorted newest first.

Ids are checked for **reuse**, because an id is how a bug is cited from a test
name, a design doc and a commit message. Eight collisions were sitting in here
when that check was added — four of them entire entries duplicated verbatim,
one symptom filed twice with different evidence, and two genuinely different
bugs sharing a number.

An entry with no `evidence:` is **refused at check time**. If you cannot name
what would prove the fix, you have not finished describing the bug.

`evidence: manual` is the one exception, for bugs no headless test can reach —
synthetic pen and hover input through Xvfb is unreliable here. Those never
auto-close; a human verifies and ticks the box. Reach for it rarely: it is the
only place in this file where a claim is the best evidence available.

**A report from outside this repo's tooling — a person, or an agent that has
not read this file — goes to `INBOX.md`, not here.** It cannot know a real
test name or a free id, so an entry it writes directly would either fail
`bugs.py check` or accidentally resolve against the wrong test. A periodic
session formalizes each inbox entry into a real one, following the rules
above, and deletes it from the inbox once it does.

```bash
python3 scripts/bugs.py check          # status; exits 1 on drift, a reused id or missing evidence
python3 scripts/bugs.py sync           # rewrite the marks and re-sort open above fixed
python3 scripts/bugs.py next           # highest-priority open bugs
python3 scripts/bugs.py mine timeline  # open bugs in one domain
python3 scripts/bugs.py stats          # counts per priority and domain
```

## Priority — severity × reach

|  | every session | common | occasional | rare |
| --- | --- | --- | --- | --- |
| **blocks work** | P1 | P1 | P2 | P2 |
| **corrupts art** | P1 | P1 | P2 | P3 |
| **wrong output** | P2 | P2 | P3 | P3 |
| **annoyance** | P3 | P3 | P4 | P4 |

*Corrupts art* outranks *wrong output* because a wrong render is visible and
recoverable; a damaged record is neither.

**Cost is not in the matrix, on purpose.** It is recorded on each entry so a
session with ten spare minutes can pick a cheap P2 over an expensive one, but
it never changes the order — folding effort into the rank is how the hard,
important bugs never get picked.

## Domains

One tag per bug, from this list, so an agent about to edit an area can find
what is already known to be wrong in it:

`brush` · `timeline` · `layers` · `canvas` · `transform` · `colour` ·
`export` · `project` · `ui` · `ai`

**The rule for an agent working in a domain:** fix its open **P1 and P2** bugs
alongside whatever you came for, each with its own regression test in the same
commit. Mention P3 and P4 without touching them — a request to change one
thing must not come back as a diff touching six. Anything needing a product
decision goes to `QUESTIONS.md` and is left alone.

- [ ] **B92** `P3` `brush` Smearing does not preserve detail, because it deposits a colour rather than moving pixels `evidence: manual`
  - Krita's two Color Smudge algorithms differ in *what* they lay down: smearing "copies the area underneath the previous position of the brush onto the new position, taking opacity into account", so texture and detail streak; dulling "picks up the colour underneath it, mixes it with its own colour, then paints with it", so detail dissolves and the brush shape is preserved.
  - `StampSmudgeDabs` implements **both** as a single averaged `SKColor` laid down through `LerpDab`. The two modes therefore differ only in how much of the local sample is blended into the carried colour — `deposit = carried` for smearing against `Mix(sample, carried, carryOver * 0.5)` for dulling — and neither can preserve detail, because a scalar colour has none to preserve.
  - The code says otherwise, which is the part that makes this worth an entry rather than a shrug: the comment above it reads *"Smearing drags a sample along the stroke and refreshes it as it goes, so detail smears into streaks"*. It does not streak; it cannot.
  - Fix is a translated patch rather than a colour — read the dab's neighbourhood from the previous dab position and composite it at the new one, weighted by the dab shape. That is a change to the deposit itself, so it collides directly with **B69/B89**'s preview work and should not be attempted alongside it. Cost: L
  - P3 because the brush is useful as it stands — it blends, which is most of what it is reached for — and because the gap is expressive rather than corrupting. Raise it if an artist asks for texture to survive a smear.

- [ ] **B71** `P3` `brush` Brush settings are lost when Lightbox closes `evidence: BrushSettingsPersistenceTests, BrushSettingsSurviveARestart, ABrushLeftAtItsDefaultsWritesNoKey`

- [ ] **B60** `P3` `brush` The brush engine assumes a read bitmap's origin is the document's origin `evidence: manual`
  - Found while fixing B59, and it is the reason B59's obvious fix made things worse rather than better.
  - `BrushEngine.SampleAverage` indexes the bitmap an effect brush reads using the dab's **document** position: `Math.Clamp((int)(pos.X + dx * spread), 0, pixels.Width - 1)`. `LerpDab` does the same, mixing `GetDeviceClipBounds` (device space) with `pos.X * outputScale` (document space). Both are correct exactly while the read bitmap covers the document from its own (0,0) — which every caller predating tiling did.
  - Nothing is broken today. `FrameRasterizer`, the live preview and the export all pass document-aligned bitmaps, so the assumption holds everywhere it is currently made. This is a latent constraint rather than a live defect, which is why it is P3.
  - What it costs is optionality: an effect brush cannot be rendered against any surface that is not document-aligned, so it cannot be tiled, cannot be rendered into a scratch around a region, and cannot be re-rendered for one viewport. `TiledRasterizer.CanTile` refuses effect brushes for exactly this reason, and that refusal is the B59 fallback.
  - Fix: thread a read origin through `StampSmudge`/`StampSmudgeDabs`/`SampleAverage`/`LerpDab` and the blur pair, defaulting to (0,0) so every existing caller is unchanged, and subtract it where the read bitmap is indexed. Mechanical, but it edits the hottest file in the repository on the path invariant 2 guards — so it wants `RuntimeDeterminismTests` green and the effect-brush suite unchanged as its evidence, not just a compile. Cost: M
  - Closing this is what lets an effect brush tile properly and retires B59's whole-frame fallback. `EffectBrushesAreRefusedByTheTiledPathUntilB59IsFixedProperly` is written to fail on that day and say so.

### canvas

- [ ] **B144** `P1` `canvas` Playback re-rasterizes most of the scene every pass above 720p, because the frame cache budget is a fixed 512 MB `evidence: manual`
  - Repro: a 24-frame, 3-layer animation, played in a loop. Measured on the **second** pass, so the first-pass rasterization every document must pay is excluded. `AnimationSweeps.PlaybackCanvasSize`, budget 83 ms at 12 fps:

    | canvas | p50 | p95 | resident | needed | effective fps |
    | --- | ---: | ---: | ---: | ---: | ---: |
    | 720p | 24.3 ms | 27.4 ms | 72 of 72 | 265 MB | 41 |
    | 1080p | 136.7 ms | 188.2 ms | 64 of 72 | 597 MB | **7** |
    | 1440p | 181.3 ms | 229.2 ms | 36 of 72 | 1.06 GB | **6** |
    | 4K | 314.6 ms | 356.7 ms | 16 of 72 | 2.39 GB | **3** |
  - **`n^2.25`, and the exponent is the tell.** Compositing is `n^1.03` — linear in area, as it must be. Playback is squared because two costs multiply: each frame costs more *and* fewer frames fit, so the miss rate climbs with the same area that makes each miss dearer. A budget expressed in bytes against bitmaps that grow with area gives a frame count that falls as the square.
  - Cause: `FrameBitmapCache.ByteBudget` is `512L * 1024 * 1024`, a compile-time constant with a preference beside it. A cached bitmap is `w * h * 4`, so the budget buys 141 frames at 720p, 62 at 1080p and 15 at 4K, against a scene that wants 72 — one per layer per frame. Above 720p the LRU evicts frames the next pass needs, and `EvictionOrder.MostRecent` (the scan-resistant flip, which is right) cannot help when the working set simply does not fit.
  - **Distinct from B29 and B125, which are the other half of the same stall.** Subtracting `CanvasSize` (3 layers, 1 frame, every access a hit) from this scenario splits it: at 1080p, 55.7 ms is compositing and **81 ms is re-rasterizing**; at 4K, 215.0 ms is compositing and **100 ms is re-rasterizing**. So B29/B125 own the majority at 4K and this bug owns the majority at 1080p, and fixing either alone leaves playback over budget at both. Filed separately because the fixes are unrelated — a budget that reads available memory, versus compositing that is not full-canvas CPU raster.
  - **The bench measures the worst case for the composite half and the exact case for this half.** `Composite` in the harness composites at scale 1.0; the application uses `ComposeScale`, which renders at the resolution the window can show (~40% for a 4K document on a laptop), so the real blit is cheaper. The cache stores full-document bitmaps either way — `_cache.Get(frame, scene.Width, scene.Height, …)` — so the miss cost transfers unchanged.
  - P1 rather than P2 on the strength of the number: 1080p is not an exotic size, 7 fps is not playback, and flipping drawings is the pillar-1 activity the application exists for. B29 and B125 stay P2 because each is a ceiling; this one is a constant that can be raised.
  - **Fix, and the first part is nearly free**: size the budget from installed memory rather than a literal, with the preference as an override rather than the only lever — a machine with 32 GB can hold a 1080p scene several times over and is currently held to 512 MB. That alone should take 1080p from 137 ms to about 56 ms, inside budget. 4K needs 2.4 GB for a 24-frame scene and cannot be solved this way at every length, which is where the checkpoint (B30) and the tile path stop being separate work.
  - **The measurement gap that hid this is worth more than the bug.** `AnimationSweeps.Playback` has always existed, times the identical operation, and never saw it: it runs at 720p and sweeps *frame count*, which is the one axis playback is flat on. Every recorded playback row sat inside budget while the application was at 7 fps on an ordinary document. A sweep is evidence about the axis it sweeps and about nothing else, and a scenario that fixes the axis an artist would name is not measuring their workload.

- [ ] **B125** `P2` `canvas` Layer compositing is entirely CPU raster, which is the ceiling left at 4K `evidence: manual`
  - Split out of B122 rather than left inside it: B122's upload half landed and its checkbox is derived, so leaving this in the same entry would have marked "compositing is on the CPU" fixed when only the transfer was. Reported still-lagging at **4K at 180 dpi** after B121 and B122, mildly improved — which is what a CPU composite of 8.3 megapixels per whole-canvas publish looks like once the transfer stops dominating.
  - Every compositing surface is CPU raster: `SKSurface.Create(SKImageInfo)` with no `GRContext` at `ComposeRing.cs:94`, `SceneRenderer.cs:72`, `MainViewModel.cs` (culled and unbounded paths), and `FrameRasterizer.cs:28` is a CPU `SKBitmap` plus a CPU `SKCanvas`. Nothing in the solution ever creates a `GRContext`.
  - **The status bar reads "GPU" and means only that Avalonia can accelerate the final blit.** `CanvasControl.GraphicsBackend` says nothing about where layer compositing happened, and it misled the owner exactly as written — so the wording is part of this entry rather than incidental to it.
  - Three constraints any fix has to respect, and the first is absolute: the **brush engine must stay on the CPU**, because `RuntimeDeterminismTests` pins a bit-identical fingerprint of the render path and GPU rasterisation is not bit-identical across vendors or drivers — invariant 1 makes the stroke record the document, so a stamp that cannot be reproduced breaks reload, undo re-render and inbetweening. **Readback** is the second: `GetPixel`/`ReadPixels` in `BrushEngine` (smudge and blur sample the canvas), `FloodFill`, `SymbolRasterizer`, `TextureRegistry` and `TiledRasterizer` each become a pipeline stall against a GPU-resident canvas. **Display-versus-export divergence** is the third: two blend implementations is the shape of B54 and B69, which is why contact sheets exist for it.
  - So the plausible fix is *not* "composite on the GPU" wholesale. Wants a design note and an owner decision. Cost: L
  - **There is now a way to measure this rather than argue about it.** `Help ▸ Write a render report` (`RenderReport`) writes what the drawing path actually did on the artist's machine into the diagnostics folder — backend, whether the durable frame is really GPU-backed, texture limits, compose surface size, session counters, and an upload probe timed on the real hardware. It exists because this repository's suite structurally cannot answer those questions: there is no GPU context in the container, which is why B122's saving shipped as an inference. The probe's speedup is the discriminator — **near 1× on a GPU-backed surface means the transfer is not the remaining cost and this entry is**.
  - **A cheaper lead worth measuring first, found in the publish trace rather than reasoned about.** Incremental publishes were repainting the whole canvas anyway — `dirty={686,386,28,28} clip=` with a null clip, at 18–20 ms on a 4K document — because every whole-canvas publish marks the other two `ComposeRing` buffers `NeedsFull`, and `CatchUpIdleBuffers` only runs when `dirty is not null`. Every `EndStroke` publishes whole-canvas, so the first pointer events of each stroke land on a buffer that repaints in full. If committing a stroke dirtied only the stroke's bounds, or idle buffers were caught up across full publishes too, that cost would go without touching the CPU/GPU question at all. Unmeasured as a fix; the 18–20 ms and the null clips are measured.
  - **The 4K ceiling now has a number rather than an argument.** `AnimationSweeps.CanvasSize`, 3 layers, every access a cache hit — so this is compositing with no rasterization in it: 13.4 ms at 960×540, 55.7 ms at 1080p, 99.0 ms at 1440p, **215.0 ms at 4K** and 1040.6 ms at 8K, against an 83 ms playback budget. `n^1.03`: linear in area, which is correct for full-canvas CPU blits and is exactly why it cannot be tuned out. 4K is 2.6× over budget on cache hits alone, so even a cache that never missed would leave playback at ~4.6 fps.
  - Measured at compose scale 1.0. The application composites at `ComposeScale` — a 4K document in a laptop window is ~40% — so the real figure is lower and the *shape* is the same; the ceiling arrives at a bigger canvas, not never.

- [ ] **B30** `P2` `canvas` A painting takes minutes to rebuild from its strokes, and opening one is the whole cost `evidence: manual`
  - **Re-ranked P3 → P2 on 2026-08-08, and re-titled, because the P3 was resting on an assumption that is false for half of what this application is for.** The reasoning below the rule read *"a miss is currently rare on a scene that fits the cache"* — true of one frame in a sequence, and not true of a single painting, where there is one cel, no timeline to cache siblings from, and the document *is* the frame you keep missing on. Nobody had measured that case: the sweep stopped at 800 strokes with a 9 px line-art brush, which is the animation half's shape.
  - `AnimationSweeps.PaintingRebuild` now sweeps a painting-shaped workload — 1920×1080, 60 px soft brush, 0.05 spacing, flow 0.5:

    ```
    strokes      p95     per stroke   allocated
        250   2 680 ms     10.7 ms      18.7 MB
        500   5 289 ms     10.6 ms      37.4 MB
      1 000  10 714 ms     10.7 ms      74.8 MB
      2 000  21 116 ms     10.6 ms     149.5 MB
    ```

  - **`n^1.00`, and the smallest sample is already 27× over the 100 ms budget.** There is no cliff to avoid — the cost accumulates linearly and never comes back down. Measured by hand at 2000×1500 past where the sweep will sit still: **10 000 strokes is 106 seconds**, and 10 000 painterly strokes is not an unusual painting, it is a finished one. Allocation at ~75 KB a stroke is a second cost: 150 MB of garbage to open a document lands on the interaction that follows it.
  - **It is fill rate, not dab count, and the intuitive answer points the wrong way.** Spacing is a fraction of brush size, so a 60 px brush at 0.05 steps 3 px against a 9 px brush at 0.1 stepping 0.9 px — the big soft brush lays *fewer* dabs per unit length. The two scenarios are sized to ~110 dabs a stroke each so the comparison isolates area: same dabs, **44× the coverage per dab, 5.3× the time** (2.0 ms a stroke for line art against 10.6). Cutting dab counts would buy nearly nothing.
  - **The tiling this entry already names as the fix does not reach it, for two reasons, both checked.** `TileFrameCache` and `TilePyramid` landed in PR #85 — but the canvas only takes that path behind `UnboundedCanvasOn` (`MainViewModel.cs:111`, `:10018`), so every bounded document pays the full replay; and `TilePyramid` builds its reduced levels by downsampling level 0, so a painting viewed whole needs every tile at full resolution, which is every stroke again. **Tiling defers work you cannot see, and a painting viewed whole has nothing to defer.** Un-gating it is still worth doing for working zoomed-in on a large canvas; it is a different bug.
  - Fix: the raster checkpoint this entry proposed, now designed rather than gestured at — `docs/DESIGN-raster-checkpoint.md`. The load-bearing finding there is that it **must not reuse `Frame.PngBase64`**: `Materialize` draws that field and *then* replays the strokes, so a checkpoint stored in it paints everything twice; `CanTileFrame` requires `!HasBaseline`, so it would disable tiling on exactly the documents that need it; and `UnseenByTheModel` reads `HasBaseline` to mean "imported pixels the model cannot see", which a rendering of readable strokes is not. Derived state and content-with-provenance want different fields. Cost: M for the checkpoint, L if the invalidation is got wrong once and has to be rebuilt on trust.
  - **Not fixed by making the replay parallel**, worth saying because it is the first idea everybody has: the dabs are deterministic and the frame could be split into bands, but a constant factor against linear growth postpones the wall rather than removing it. Measure before believing it is enough.
  - P2 rather than P1: nothing is corrupted, no work is lost, and **drawing itself is unaffected** — invariant 6 bounds live preview and commits to the region a stroke reaches, so painting stroke 8 000 costs what stroke 8 did. What it makes slow is opening, undoing deep, and exporting.
  - Repro: rasterise a frame of 800 strokes at 1080p. Measured p95 **1594 ms**, and it passes the 100 ms per-action budget at about **100 strokes** — which is not a busy drawing, it is an ordinary one.
  - Paid on every cache miss, every undo past the top of the stack, and every frame of an export. B28 makes it worse by turning misses from occasional into constant, but the two are independent: fixing the eviction policy leaves this exactly where it is.
  - Cause: **n^1.03** — linear in strokes, so the replay itself is honest and the constant is the whole story at roughly 2 ms a stroke. Invariant 1 says the pixels are derived from the record, and this is the price of that; the question is not whether to replay but whether every miss has to replay from nothing.

- [ ] **B29** `P2` `canvas` A full recomposite costs about 20 ms a layer, so the playhead cannot be dragged `evidence: manual`
  - Repro: a 3-layer scene, drag the playhead. Measured p95 **124 ms** at 720p against a 16 ms interaction budget — the cliff is at **12 frames**, which is well inside the cache, so this is not B28. Scrubbing is simply a full recomposite and a full recomposite is not cheap.
  - The same cost, seen four ways in `PERFORMANCE.md`: recompositing by layer count breaks at **4 layers** at 1080p (476 ms at 24); onion skin breaks with **no ghosts at all**, because drawing one costs a recomposite before a single ghost is blended; playback is over its 83 ms period; scrubbing is over its 16 ms one. One cause, four symptoms — filed once, on purpose. Filing the symptoms separately would have four people fixing the same blend loop.
  - Cause: each visible layer is a full-canvas `DrawBitmap` of a premultiplied 1080p bitmap, so a recomposite is *layers × canvas area* of software src-over. Linear in layers — measured **n^0.99**, so nothing is accidentally quadratic — and the constant is simply large: about 20 ms per 1080p layer on this container.
  - Why drawing does not suffer: `ComposeRing` repaints only the region a stroke touched, which is the whole reason that class exists. The gap is that **a frame change has no equivalent** — it always goes wide.

Timed at 1920×1080 on this container — **no paint at all 18.53 ms, an empty paint 18.60, `DrawPass`'s paint 18.80.** Under one and a half per cent between them. The blit itself is the cost, at about 9 ns a pixel, so there is no cheap fix hiding in the paint and the structural ones below are the only ones there are.
  - Two things that fell out of the same measurement and sharpen the picture. A layer at **partial opacity costs 29% more** than an opaque one (23.93 ms), so layer opacity is not free.   - **Candidate 2 has landed.** "Composite at display resolution rather than document resolution when the result is only going to be shown" is `ComposeScale`, and `PublishSnapshot` has been doing it — *"Compose at the resolution the canvas can actually show.   - **Candidate 1 measured, and it is two-sided.** `SideCompositeHit` and `SideCompositeMiss` in `tools/Lightbox.Bench` price it against the existing `Layers` sweep at 1080p. A miss is **worse than doing nothing**: 463 ms against 434 at 24 layers, and the cliff moves from **8 layers to 4**, because the cache pays to rebuild the side and then pays again to blend it. Break-even is at about **3 layers**; below that it is pure overhead, since at 1 layer it is 35.7 ms against 19.5.
  - **The finding that changes the plan: even a perfect hit does not reach this bug's budget.** The hit case floors at ~35 ms because two full-canvas 1080p blits cost that much, and the interaction budget here is **16 ms**. The floor is set by blit count × canvas area, and the cache can only reduce the count — it is already at two. Getting a scrub under 16 ms therefore needs the *area* to fall, which is **B82**: composite the visible rectangle rather than the whole document. Candidate 1 is still worth building for deep stacks, where it turns a linear cliff into a flat 36 ms and rescues the playback budget it currently fails at 4 layers — but it is an improvement rather than a fix, and it should be built knowing that.

  - Found by `tools/Lightbox.Bench`, not by a report. Nobody had measured a frame change because every budget in the charter measures one stroke on one frame.
  - **The playback half of this is now measured and split from the cache half (B144).** `AnimationSweeps.CanvasSize` composites 3 layers with every access a cache hit, so it prices compositing alone: **55.7 ms at 1080p and 215.0 ms at 4K**, against an 83 ms playback budget. The test now asserts the true containment instead: **100% of the differences fall inside the smudge's own footprint**, which is what a read-neighbourhood defect can touch and nothing wider.
  - **Fixed, and not the way this entry predicted.** Effect brushes are refused by the tiled path (`TiledRasterizer.CanTile`) and their frames render whole and are sliced into the store, so the pixels come from the untiled path and cannot disagree with it. Measured: **0 differing pixels**, and the store still holds **1 tile of the 12 the document spans**, so what stays resident is proportional to ink even on the fallback. The cost is one document-sized allocation *while the frame renders* — today's peak memory, kept only for frames that actually contain an effect brush.
  - **The padded-read fix below was tried and is wrong, which is worth keeping rather than deleting.** Rendering the neighbourhood into an offset scratch made it *worse*: 3265 wrong pixels against 3876, with the worst alpha delta rising from 191 to a full **255**. The reason is the real root cause, and it is deeper than "a tile is too small to read": `SampleAverage` indexes its read bitmap with the dab's **document** position — `Math.Clamp((int)(pos.X + dx * spread), 0, pixels.Width - 1)` — and `LerpDab` does the same. The engine assumes **the read bitmap's origin is the document's origin**, which was true of every caller that existed before tiling. A shifted scratch violates that, and a sample read from the wrong place is further from the truth than one clamped short.
  - **Left open as B60**: thread a read origin through the effect path so the engine stops assuming, which is what lets an effect brush tile properly instead of opting out. Not done here on purpose — it edits the hottest and most invariant-critical file in the repository, and putting the discovery and the surgery in one diff is what the branch conventions exist to stop. `EffectBrushesAreRefusedByTheTiledPathUntilB59IsFixedProperly` pins the refusal so the fallback cannot be removed silently, and it is written to fail the day B60 lands.
  - Superseded plan, kept for the reasoning: render an effect brush against a **padded read source** — the tile plus a margin of its neighbours, at least the dab radius and the smudge sampling offset. That is a real cost (the margin is re-rasterised per tile) and it only applies to `BrushKind.Smudge`/`Blur`, so the paint path keeps the cheap read. The alternative — flatten the neighbourhood on demand — trades memory for the same thing.
  - **P2 rather than P1 because nothing renders through tiles yet.** `TiledRasterizer` is not wired into the canvas, the cache or export, so no artist can reach this today. It becomes a P1 the moment the render path moves, and it is the reason that move must not happen before this is fixed. Cost: M

- [x] **B21** `P2` `canvas` Shrink then Grow walks a selection into its top-left corner `evidence: ShrinkAndGrowLeaveTheSelectionWhereItWas, ACircleShrinksByTheSameAmountOnEverySide`

- [x] **B134** `P3` `canvas` A stroke entirely outside the document cannot be picked, and will not be findable on an infinite canvas `evidence: AStrokeOutsideTheDocumentIsStillPickable, TheIndexKeepsUnclampedBoundsForPicking`

Outline only and stroked, as the reporter asked; a filled preview hides the artwork at the moment the artist is deciding where to put a mark.
  - **The subtle half, and it was wrong in the first draft: the unit-space normalisation.** Dividing x by width and y by height is the obvious thing and it squares every non-square tip, because `StampDab` scales by `radius * 2 / Math.Max(tip.Width, tip.Height)` — *one* factor for both axes, so a 64×32 tip stamps at 2:1 and its long axis is what brush size means. An outline the right size around a mark of the wrong shape is the same disagreement this bug already is. `ANonSquareTipKeepsTheAspectTheEngineStampsItAt` reads aspect 1.02 with the fix removed and 2.03 with it.
  - Roundness and angle come from `BrushSettings.Roundness` and `TipRotationDeg` — the brush's nominal values, deliberately not `RoundnessAt` or the full rotation. Those fold in a jitter seeded from the dab's position, so a cursor built on them would wobble as the pointer moved and report the jitter rather than the brush. `AngleFollowsDirection` is excluded for a different reason: a hovering pointer has no heading, so including it would mean inventing one.
  - **What is not asserted, and why.** A rendered frame cannot be captured — the suite runs on Avalonia's headless *software* drawing, and the ring is drawn in the canvas's render op rather than into the published `RenderSnapshot`, so `LivePreviewPixelTests`' approach cannot reach it either. Turning real rendering on for 1370 App tests to reach one overlay is a large risk for a small assertion. So the silhouette is tested exactly in `BrushTipOutlineTests` (Raster, pure) and the wiring is tested as wiring in `BrushGizmoTests`; that the ring *looks* right is a `MANUAL_TESTING.md` check.

- [x] **B8** `P3` `ui` Timeline context submenu flickers under a pen `evidence: CelDragGesture, CelDragGestureTests, OpeningAContextMenuCancelsThePendingDrag, LettingGoDisarmsTheGesture`
